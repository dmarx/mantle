# DP-012: Put a seam where you'll change what's behind it

Before changing how something is represented, or what answers for it, put
one boundary in front of it. Move every consumer onto that boundary first.
Then make the change behind it.

Why: a change that has to edit every consumer at once lands as one big
risky diff. Behind a seam, it is a one-site edit, landed in steps, green at
each one, and the consumers never learn the representation moved.

Applied here:

- **Where a document comes from** (deployed bytes, a raw source URL, a
  database query) sits behind one `fetchDocument` boundary from the first
  version, because [ADR-001](../record/decisions.d/ADR-001.md) already names three answers to that question.
- **Where a view's rows come from** (committed markdown now, a graph query
  later) is a seam of its own for the same reason.

The corollary: a seam is cheap to keep but not free. Put one only where a
change is planned or has happened twice. A seam in front of everything is
indirection.
