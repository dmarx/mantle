# SOP-002: Run a session's work through a session pull request

## Purpose

The owner reviews a session as one ordered history instead of a stack of
pull requests, and each unit still gets its own checks and can be reverted
alone. Skipped, the session either becomes one tangled pull request or a
stack where every review waits on the one below.

## Before you start

- The session branch exists: the branch the session was given, or one cut
  from `main`, and it is pushed.
- You know the first unit. Later units can be named as they arise.

## Steps

1. **Open the session pull request** from the session branch into `main`, with
   a description listing the planned units, and a section for what waits on
   the owner.
   *Check:* the pull request exists, and its base is `main`.
2. **Cut a unit branch** from the session branch's *current* remote head:
   `git fetch origin <session>` then `git checkout -b <session>--<slug>
   origin/<session>`.
   *Check:* `git merge-base --is-ancestor origin/<session> HEAD` succeeds, and
   no other unit's unmerged commits are in `git log origin/<session>..HEAD`.
3. **Do the unit** with its record entries (a changelog fragment named after
   the unit branch, a decision with its first application or its source).
   Push as you go.
   *Check:* every commit is pushed (local and remote heads match).
4. **Open the unit pull request with base = the session branch**, not `main`.
   *Check:* the pull request's base branch reads `<session>`.
5. **Wait for its checks, then squash-merge it** with the unit's title as the
   commit subject and a body saying what and why. Pull the session branch.
   *Check:* the session branch has exactly one new commit for the unit, and
   the docs-check run on the unit pull request was green.
6. **Update the session pull request's description**: read it just before
   writing, add the unit to the list, and change only your own section.
   *Check:* the description lists every merged unit.
7. **Repeat from step 2** for the next unit. When the session ends, run
   [SOP-001](SOP-001.md), and leave the session pull request to the owner, who merges it
   **with a merge commit**.
   *Check:* the session pull request's commits read as one commit per unit,
   in order.

## Done when

Every unit is squash-merged into the session branch, the session pull
request describes them all and is green, and the owner has been told it is
ready to review.

## Pitfalls

- **Cutting a unit from another unit's branch.** That is the stack this
  procedure removes. Wait for the first unit to merge into the session branch.
- **Opening the unit pull request against `main`**, which some tools default
  to. Check the base in step 4.
- **Squash-merging the session pull request.** That collapses the history the
  review is for. The session pull request is the owner's to merge, with a
  merge commit.
- **A bot repair commit on the unit branch after the squash.** If docs-check
  pushes a repair after you merged, it lands on a dead branch. Wait for the
  check to finish (step 5), and pull before merging.
