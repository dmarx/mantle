# ADR-005: Work is a logical unit per pull request, squash-merged into a session pull request whose commits are the review

## Context

The assistant opens pull requests quickly and the owner reviews them, so the
shape of a pull request decides whether review is possible.

- **A unit per pull request** came from nucleation ([NU-ADR-071](https://github.com/dmarx/nucleation/blob/main/record/decisions.d/ADR-071.md)): a pull
  request mixing units can't be accepted in part.
- **One pull request per unit, all into `main`**, led to deep stacks: each
  unit cut from the previous one's branch, to be merged in order, rebased
  whenever one changed. The owner reviewed a stack of related pull requests
  where one coherent story was wanted.
- **nucleation's standing `staging` branch** ([NU-ADR-116](https://github.com/dmarx/nucleation/blob/main/record/decisions.d/ADR-116.md)) removes the
  stacking, at the cost of a second long-lived branch and a nightly
  promotion. mantle's `main` deploys, and should stay simple.
- **A session pull request** is the variant the owner is running in
  nucleation's dialectic sessions, and it is working. Units merge into the
  session's own branch, and the session reaches `main` as one reviewable
  history.

A second question is when a decision needs a demonstration. [NU-ADR-071](https://github.com/dmarx/nucleation/blob/main/record/decisions.d/ADR-071.md) asks
for each decision's first application in the same pull request. That guards
against a rule that reads well and lands wrong. But a convention the owner
already runs in another project has had its first application, there, and
re-demonstrating it in an empty repository proves nothing new.

## Decision

*Proposed.*

**Session branch and pull request.** A working session has one branch, cut
from `main` (or the branch the session was given), and one pull request
from it into `main`, opened at the session's first unit. Its description
lists the units and what waits on the owner. The owner reviews it as a
sequence of commits and merges it **with a merge commit, never a squash**,
so `main` keeps one commit per unit, and `git log --first-parent main` shows
one entry per session.

**Unit pull requests.** Each logical unit is what a reviewer would accept or
reject whole: one decision with what it changes, one feature, one dependency
bump, one sweep. Each gets:

- a branch cut from the session branch's current head, named
  `<session-branch>--<unit-slug>`;
- a pull request into the session branch;
- once its checks are green, a **squash merge** by the assistant, with the
  commit message being the unit's title and a body saying what and why.

A unit that needs another unit's work is cut *after* that unit has merged
into the session branch, never from its branch. **No stacks.**

**A session of one unit** can skip the indirection: its single pull request
goes straight into `main`, and that is also the session pull request.

**When a decision needs its first application here.** A decision, principle
or SOP that is new to the owner's projects carries its first application in
its unit's pull request, citing it. One adopted from a sibling record, where
it is already in use, cites that record's decision as its application
instead.

**Push as you go:**

- Push each commit as it is made.
- The record's docs-check repairs and lints every pull request, unit or
  session, so `luria repair`, `index` or `lint` don't need running as a gate
  before a push. Running one narrowly to diagnose a red check is fine.
- Pull before each push, since the bot's repair lands as its own commit.
- **Code is different:** typecheck and unit tests run locally before a
  push.

**Persist as you go.** Work that runs past a few tool calls, and all
delegated work, lives on its unit branch from its first step and pushes
after each step. Its brief and working notes are in the repository, not a
scratch directory, so a stop loses at most the step in hand.

The steps are [SOP-002](../procedures.d/SOP-002.md).

## Alternatives considered

- **Unit pull requests stacked into `main`.** This is what produced the
  stacks. Each review depends on the ones below it, and a change low in the
  stack rebases everything above.
- **One pull request per session, committed directly.** No unit can be
  reviewed, checked or reverted on its own, and the history is whatever order
  the commits happened in.
- **A standing staging branch** ([NU-ADR-116](https://github.com/dmarx/nucleation/blob/main/record/decisions.d/ADR-116.md)). It solves the same stacking,
  but adds a branch that outlives sessions, a promotion job, and back-merges.
  A session branch is born and dies with its session.
- **Squash the session pull request too.** That collapses the session's units
  into one commit, the history the review was organised to show.
- **Rebase-merge the session pull request.** It keeps the unit commits but
  drops the session boundary from `main`'s history. The merge commit is what
  groups a session's units.

## Consequences

- **The assistant merges into the session branch**, not into `main`. That is
  reversible, since the owner reviews the whole session before anything
  reaches `main`. Merging into `main` stays the owner's ([ADR-004](ADR-004.md)).
- **docs-check runs on unit pull requests** as well as the session's,
  because the Docs workflow's `pull_request` trigger has no branch filter.
- **Numbering across sessions.** mantle numbers decisions when they are
  filed, so two sessions running at once can claim the same next number. The
  sequential units of one session can't collide. If concurrent sessions
  become normal, the ADR scheme moves to luria's `merge` allocation
  ([LU-ADR-049](https://github.com/dmarx/luria/blob/main/record/decisions.d/ADR-049.md)).
- **First application, this session:** this revision and [SOP-002](../procedures.d/SOP-002.md) are a unit
  pull request into this session's branch (dmarx/mantle#1), squash-merged
  there. So are the conventions adopted after it.
