# ADR-005: Work is a logical unit per pull request, carries its first application, and persists as it goes

## Context

The assistant opens pull requests quickly and the owner reviews them, so
the size and shape of a pull request is what decides whether review is
possible. nucleation learned three things here:

- a pull request mixing units can't be accepted in part ([NU-ADR-071](https://github.com/dmarx/nucleation/blob/main/record/decisions.d/ADR-071.md));
- a decision approved in the abstract can come out wrong in use (the same
  ADR);
- a cloud session and its scratchpad can disappear mid-task, taking
  unpushed work with them ([NU-ADR-141](https://github.com/dmarx/nucleation/blob/main/record/decisions.d/ADR-141.md)).

It also learned that running the record's repair and lint locally before
every push duplicates CI ([NU-ADR-054](https://github.com/dmarx/nucleation/blob/main/record/decisions.d/ADR-054.md)).

## Decision

*Proposed.*

- **One logical unit per pull request**: one decision with what it changes,
  one feature, one dependency bump, one sweep. If a reviewer could
  reasonably want one part without another, they are two units.
- **A decision goes with its first application.** The pull request that
  proposes an ADR (or adopts a principle, or adds an SOP) carries the first
  change made under it and cites it. The reviewer approves the rule by what
  it does, and `git blame` leads from the decision to its effects.
- **Push as you go.** Open the pull request early and push each commit as it
  is made. The record's docs-check repairs and lints on the pull request; don't
  run `luria repair`, `index` or `lint` as a gate before pushing. A narrow
  local run to diagnose a red check is fine. Pull before each push, since the
  bot's repair lands as its own commit. **Code is different:** typecheck and
  unit tests run locally before a push, because a red code check costs a
  review round trip.
- **Persist as you go.** Work that runs past a few tool calls, and any
  delegated work, lives on its branch from its first step and pushes after
  each step. Its brief and working notes are in the repository, not a
  scratch directory. A stop at any moment loses at most the step in hand.

## Alternatives considered

- **One pull request per session.** Easy to open, impossible to accept in
  part. The owner either takes everything or untangles it.
- **Decisions first, application later.** The rule reads well and lands
  wrong, and nobody finds out until the first use, by which time the
  decision is citable as settled.
- **A staging branch with nightly promotion** ([NU-ADR-116](https://github.com/dmarx/nucleation/blob/main/record/decisions.d/ADR-116.md)). It solves stacked
  pull requests and temporary codes cited across units. mantle has neither
  problem yet, and its `main` deploys to Pages, so it should stay simple.
  Revisit when [ADR-002](ADR-002.md)'s batch trigger keeps firing or stacks get folded.

## Consequences

- **Not applied retroactively.** mantle's first pull request carries [ADR-001](ADR-001.md)
  to ADR-005 together, because that pull request founds the record. This rule
  applies from the next one.
- CLAUDE.md states the four rules briefly and points here.
