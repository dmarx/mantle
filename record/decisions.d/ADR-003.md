# ADR-003: Step-by-step processes are SOPs: a scheme of their own, implementing the decisions that hold their rules

## Context

Some of what a project knows is procedure: how to close a batch of work, cut
a release, move a site onto mantle, bump a pinned dependency. Procedure has a
different life from a decision. A decision is made once and superseded when
the choice changes. A procedure is run repeatedly, and every run can show a
step that is wrong, missing or in the wrong order. Fixing a step is routine,
not a new decision.

nucleation separates the two already: an ADR holds the invariants and a
skill file (`.claude/skills/<name>/SKILL.md`) holds the steps. For example,
ADR-068 and the `read-and-file` skill. But a skill file sits outside the
record. Nothing lints it, cites it, versions it or lists it in an index, and
a human reader has to know it exists.

mantle's [ADR-002](ADR-002.md) already implies one procedure (checking the review triggers
when a batch closes), and the publisher will need more: releasing, and
migrating a record from Quartz.

## Decision

*Proposed.* A scheme, **SOP** (standard operating procedure), in
`record/procedures.d/`, with its index at `docs/procedures/`.

- **Fixed sections**, from the scheme's `_template.md`: Purpose, Before you
  start, Steps, Done when, Pitfalls. Each step is an action plus a *Check:*,
  an observable sign that it worked, so a run can't drift into "assumed
  done". The template is the convention, so `luria new sop` produces it.
- **Fields:** a required `when` (one sentence: the occasion that calls for the
  procedure), `status` from the shared statuses, open `tags`, and the
  standard `version` and `history`.
- **`implements`** names the decisions whose rules the procedure carries out.
  The decision shows them as `procedures`, derived, so a reader of a rule can
  find how it is run, and a reader of a step can find why.
- **Revised in place.** When a run shows a step is wrong, the SOP is fixed in
  the same pull request, with `version` bumped and a `history` entry saying
  what the run found. It is superseded only when the process itself is
  replaced.
- **An assistant follows an Active SOP** when its `when` matches the task,
  and reports any step that didn't hold. A skill or other assistant
  instruction for the same process points at the SOP instead of restating
  it, since a restated copy drifts.

## Alternatives considered

- **Steps in the ADR body.** That ties a routine fix to the decision's
  supersession rule: either a decision gets edited for every changed step, or
  the steps go stale to protect it.
- **Skill files only.** They are invisible to the record's index, lint and
  citations, and they are written for an assistant, not a human. They are
  still the right place to *invoke* a procedure from; the SOP is what they
  point at.
- **A README of checklists.** One shared file every procedure edit touches,
  with no codes to cite and no version per procedure.
- **Wait until there are several procedures.** The first one exists already
  (closing a batch, under [ADR-002](ADR-002.md)), and a convention set by its first entry is
  cheaper than one retrofitted onto five.

## Consequences

- `luria.yaml` gains the SOP scheme, and ADR the derived `procedures`.
- CLAUDE.md's map names procedures and says to follow an Active one.
- **First application, in this pull request:** [SOP-001](../procedures.d/SOP-001.md), closing a batch of
  work, which implements [ADR-002](ADR-002.md). Its pitfalls come from this session: state
  reported from memory, and a shallow clone that showed no upstream for a
  branch that had already been pushed.
